# ReOpSy daily discovery: engineering decision brief

**Decision (24 November 2026):** Make Today a finite, explainable update for followed topics and make saving to a review as easy as opening a source. Keep the already-verified one-paper snap. Extend coverage with OpenAlex first, Crossref selectively; keep arXiv for matching STEM topics, and use Europe PMC only for life-science tracks. A daily discovery tool is not a comprehensive systematic search.

## Product and research evidence

| Comparator | Worth borrowing | ReOpSy's distinction |
| --- | --- | --- |
| [Semantic Scholar Research Feeds](https://webflow.semanticscholar.org/faq) | Daily recommendations follow a library folder; saved items and “not relevant” feedback steer results. The pool may include papers from the last three months. | Separate “published recently” from “discovered in this update”; let people mute a topic and reverse a decision. |
| [ResearchRabbit collections and alerts](https://learn.researchrabbit.ai/en/articles/17884627-how-do-i-get-alerts-for-new-papers), [Litmaps Monitor](https://docs.litmaps.com/en/articles/9126249-monitor-get-alerts-for-important-research) | Tracking from saved papers is useful when terminology varies. Citation alerts complement keyword/topic search. | Start with named, editable topics and a plain-language “Why this paper”; add citation-neighbor discovery as an explicit option, not hidden ranking. |
| [Elicit review workflow](https://support.elicit.com/en/articles/14759154-systematic-reviews-in-elicit), [export](https://support.elicit.com/en/articles/14758189-export-your-data-from-elicit) | Organize screening, evidence extraction and export separately from discovery. | Today should ask for one low-friction decision; Library should preserve provenance, notes and review lists. Don't claim PRISMA compliance on the basis of a feed. [PRISMA 2020](https://doi.org/10.1136/bmj.n71) and [PRISMA-S](https://doi.org/10.1186/s13643-020-01542-z) are useful later for reporting source/query/date and screening decisions. |

[Rosenholtz et al.'s visual-clutter experiments](https://doi.org/10.1167/7.2.17) support making the focal item easy to find among nearby visual elements; they do not validate one particular card layout. [Pirolli & Card's information-foraging work](https://doi.org/10.1145/223904.223911) motivates a clear title, one useful finding and recognizable source cues before a reader decides to open Details. [A field study of scrolling interventions](https://www.uni-ulm.de/fileadmin/website_uni_ulm/iui.inst.100/1-hci/hci-paper/2025/CHI2025___Scrolling_in_the_Deep__9_.pdf) reports context-sensitive responses; extrapolate cautiously from social media. [The choice-overload meta-analysis](https://doi.org/10.1086/651235) reports substantial variability and near-zero mean effect, so treat a compact card and bounded deck as design hypotheses to test, not claims about universal psychology.

**Implement now:** Keep a visible finite end/position, one obvious review-save action, Undo, and accessible labels/selected state for universal navigation icons. Keep Details, source, comment and share discoverable without cluttering the finding; don't hide every action behind unlabeled symbols. Prefer no animation for reduced-motion users, alternative next/previous buttons for swipes and keyboard controls, and generous hit areas. These align with [WCAG animation from interactions](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions), [dragging alternatives](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html), [pointer cancellation](https://www.w3.org/WAI/WCAG22/Understanding/pointer-cancellation.html) and [target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html). Test “Can I identify the method/claim and add it to a review in seconds?” and off-topic/Undo rates, not dwell time or maximum swipes. No auto-advance, new gambling-like rewards or forced social sign-up.

| **Europe PMC / PubMed** | Biomedical/life-science indexing plus Europe PMC preprints; not a baseline for management. ## Architecture and safeguards

- **Close the actual data gap first.** GitHub Nightly ingest currently upserts Supabase; the shipped client reads Firestore `feeds/latest` or uses a bundled feed, so a green scheduled job alone is not evidence that a researcher got a fresh deck. Pick one canonical publisher/reader path. Start with a testable, opt-in bridge or a read-only service adapter using only public fields; do not provision or assume credentials. Retain the prior valid snapshot on source failure, say “last updated” and distinguish source outage, demo data and an honest quiet day. Do not fill with fake papers.
- **Topic-first discovery.** Store display label, normalized query, provider filters and optionally canonical seed IDs separately. Reuse fetch results for identical normalized queries; throttle unbounded custom searches and schedule bounded jobs. Start with public examples (e.g. “organizational change”, “supply chain resilience”, “EEG classification”) without assuming anyone’s private research topic. Do not expose private topic strings in public snapshots or send them to a third party until that data path is made clear. Preserve cross-topic membership; dedupe only the visible deck. Prefer normalized DOI, then source IDs with version, then explicit preprint/version relationships; title + author/year only as a cautious fallback. Keep identifiers and source provenance.
- **Do not call a recycle fresh.** Track `publishedAt`, `indexedAt` where provided, `firstSeenAt`, and `feedGeneratedAt` separately. A source backfill belongs in “new to your feed,” not “published today.” Explicitly distinguish a preprint revision or correction from a newly discovered work. Refresh on return to foreground or manual pull, not on every swipe. Mark cache or fallback states visibly.
- **Evidence contract.** Each claim should point to one exact DOI/arXiv/PMID version and to the part of the source read. If only bibliographic data is available, say so and show metadata plus a link, not an inferred finding. Design provenance fields for summaries: source URL, reading scope (abstract/full text), license, method/findings/limitations (unknown allowed), and generation date. Never invent sample size/effect, silently generalize causes, or substitute the first fuzzy title hit. The current OpenAlex/arXiv extractive summarizer selects near-verbatim sentences even when the raw abstract is hidden; treat summaries as a separate reuse surface, make the license allowlist exact, and disable uncertain extractive reuse. The existing Semantic Scholar TLDR title-only match is not version-safe. Paper figures require a verified figure license/permission, attribution and useful alt text; prefer no image over a synthetic figure mistaken for evidence.
- **Next milestones, not this delivery.** Private named review lists and export with source and screening notes first; then optional seed-based alerts, topic communities with opt-in identity and moderation, and eventually citations/provenance-aware writing or registered reviews. Do not gate paper reading/saving on community membership. Validate small-phone/laptop/keyboard/reduced motion, two unrelated disciplines, duplicated preprint+DOI, delayed indexing, source timeouts, and one stable cold-start/no-feed state.

## Provider activation

The existing Render/Firebase feed pipeline uses server environment variables, not ChatGPT subscriptions or Firebase client-side key fields. The prior GitHub Actions path only wrote to Supabase. The bridge in this change publishes to the Firestore collection the app actually reads, only when the repository variable `REOPSY_PUBLISH_FIRESTORE_FEED` is explicitly set to `true` and the server-side `FIREBASE_SERVICE_ACCOUNT` secret is configured for the correct project. A full successful run is required; topic-only, dry and PR runs do not publish. Keep the legacy Render cron from publishing the same document once this becomes canonical. Check an authenticated production run before promising fresh papers.

Provider selection on the new nightly publishing path is off by default. To enable it deliberately, configure a supported `GEMINI_SUMMARY_MODEL` and an explicit `AI_SUMMARY_REQUEST_LIMIT` (maximum 30 provider attempts per run) alongside the existing server-side `GEMINI_API_KEY`. Optional xAI fallback additionally requires `ALLOW_XAI_SUMMARY=true`, an `XAI_SUMMARY_MODEL` and the existing server-side `XAI_API_KEY`; confirm billing and rate limits first. Check [Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing), [Gemini rate limits](https://ai.google.dev/gemini-api/docs/rate-limits), and [xAI team/model rate limits](https://docs.x.ai/developers/rate-limits) in the actual project, not in chat. Quota or authentication errors stop that provider for the run. Missing configuration or untrusted output falls back to an eligible original-source excerpt or metadata with a source link. Only public, explicitly CC BY/CC0 abstract sentences are sent to providers, and their response can select an existing sentence, not generate new claims.

The first cross-disciplinary preset is **Management & Organizations**, backed by [OpenAlex field 14](https://api.openalex.org/fields/14). The MVP does not yet schedule arbitrary private keywords or claim comprehensive management coverage. The staged UI lets readers open a source-linked brief and see whether the current snapshot is live, older or sample data.
